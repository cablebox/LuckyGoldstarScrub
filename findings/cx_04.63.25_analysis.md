## 1. The boot-time "software update available" modal — SOLVED

### 1.1 The component and the exact UI string

The modal is created by the native update daemon `usr/sbin/update` (com.webos.service.update,
586,328-byte ARM PIE). [OBS]

Exact text (rodata, [OBS]):
- `"The latest version of the software is available for your TV. Do you want to update now?"`
- message format string: `"%s<br>(%s: %02X.%02X.%02X)<br>%s"` (text + version + footer)
- footer: `"* Please use LG TV Remote Control."`

### 1.2 The exact call path

`usr/sbin/update`, function `NSU_CreateUpdateAlert` (symbol string at rodata 0x66ba4), builds this
alert [OBS — disassembly of function + rodata 0x68010–0x6808c]:

```
luna://com.webos.notification/createAlert
  alertId: "NSUUpdateAlert"            (rodata 0x682e8)
  type:    "modal"                     (rodata 0x62c68)
  message: "The latest version of the software is available for your TV.
            Do you want to update now?<br>(Software Update: 04.7x.xx)<br>
            * Please use LG TV Remote Control."
  buttons: [{ label, onclick: "luna://com.webos.service.update/startUpdate",
              params: {confirm, ...}, focus }]
```

The alert is rendered by `com.webos.app.notificationcenter` (webapp; `main.js` references
`com.webos.notification` and `modal`) on top of the launcher UI — matches the live observation that
"the launcher draws it, no separate app process". [OBS]

`NSU_TimerCreateAlert` (rodata 0x66c28) waits for locale + rolling-screen conditions, calls
`NSU_CreateUpdateAlert`, and schedules `adapter_update2noti_sendCloseAlert` →
`luna://com.webos.notification/closeAlert` — that is the auto-dismiss (~30 s live behavior). [OBS]
[LIVE] consistent.

### 1.3 Why the live box still shows it although "update is masked"

The systemd unit that was masked on the live box does NOT run the daemon:

```
etc/systemd/system/update.service   (also lib/systemd/system/update.service)
  Type=oneshot, RemainAfterExit=yes
  ExecStart=/usr/bin/luna-send -n 1 -f luna://com.webos.service.update/com/palm/luna/private/ping '{}'
```

[LIVE] This is the smoking gun: masking `update.service` only removed the ping.

The daemon is D-Bus activated on demand [OBS]:

```
usr/share/dbus-1/services/com.webos.service.update.service
usr/share/dbus-1/system-services/com.webos.service.update.service
  [D-BUS Service] Name=com.webos.service.update  Exec=/usr/sbin/update  Type=dynamic
```

Boot-time callers that re-activate it via `getStatus` [OBS]:
- `usr/sbin/tvpowerd` → `luna://com.webos.service.update/getStatus`
- `usr/sbin/eplmanager` → `getStatus`
- `usr/sbin/contentminer` → `getStatus`
- `usr/sbin/legacy-broadcast` → `getStatus` (+ enterISPMode/getProgress)
- (`factorymanager`, `homekit`, `remotediag` also reference it)

There is also a legacy upstart-style job `etc/init/update.conf` (`start on minimal-boot-done`,
exec `/usr/sbin/update`); on this image bootd (usr/sbin/bootd, "simplified upstart-like component")
emits minimal-boot-done, so this job is a second possible spawn path. [OBS files; INF activation]

### 1.4 Why the network blackhole didn't stop it

The check does not use lgtvsdp.com / su*.lge.com. Endpoints in the binary [OBS]:

- `http://nsu.lge.com:5100/` — primary NSU check (NOT blackholed on live box)
- `https://snu.lge.com/CheckSWAutoUpdate.laf` (+ CheckSWManualUpdate/DownloadResult/SWDownload*Log)
- `https://snu-dev.lge.com/...` (dev)
- `http://156.147.69.32:8080/CheckSWAutoUpdate.laf` etc. — hardcoded IP fallback (DNS immune)
- `http://su.lge.com/`, `https://su-ssl.lge.com/` (the ones the live box DID blackhole)

So every boot: daemon spawns → waits for internet → auto version check succeeds via
nsu.lge.com:5100/snu.lge.com → response parsed (`gNsuResponseUpdate`) → `NSU_CreateUpdateAlert`
→ modal. Nothing is cached; the modal is re-created from a fresh check every boot. [INF from
flow strings; consistent with LIVE "appears at every boot"]

`.lastNSUUpdateFailLog` is `/mnt/lg/cmn_data/.lastNSUUpdateFailLog`, the last-check failure log
written by the same daemon; its presence at 2026-10-22 10:50 just proves the daemon ran and
attempted the check. [OBS path; LIVE consistent]

### 1.5 Why the settings-file edits didn't work

The daemon subscribes via `com.webos.settingsservice` and parses these keys [OBS — rodata
0x66cd4–0x6747c]:

- category `hotelMode`: `enableHotelMode`, `enableLimitedMode`, `swUpdateEnable`,
  `swUpdateNotice` — gates:
  - `enableHotelMode` → `_gbEnableHotelMode`
  - `swUpdateEnable` → `_gbEnableSoftwareUpdateMenu`
  - `swUpdateNotice` → `_gbEnableSoftwareUpdateNotice`
  - explicit guard string: `"ERROR : Do not create NSU Alert when hotel mode is enable if notice
    is disable."` and `"## Disable auto version check in hotel mode if notice is false - do not
    start NSU auto update"`
- category `support`: `automaticUpdate`, `softwareUpdateEnable`
  (`etc/palm/defaultSettings.json` lines ~361458–361461: `"automaticUpdate": "off"`,
  `"softwareUpdateEnable": "true"`; region variants flip automaticUpdate on)
- category `hotelMode` defaults (etc/palm/defaultSettings.json ~line 41423): `"swUpdateEnable":
  "on"`, `"swUpdateNotice": "off"`

[LIVE] explanations:
- Editing `hotelMode.swUpdateEnable` did nothing because the consumer TV has `enableHotelMode`
  off/absent — the whole hotel gate only suppresses when hotel mode is ENABLED. Absent keys are
  never materialized in /var/luna/preferences/*, which is why "no swUpdate keys" were found there.
- db8 `/var/db/main`, sdx cache, /mnt/lg/cmn_data/{update,swupdate} are genuinely not the source;
  nothing is persisted for the notice. WAM localStorage is a red herring — no component in the
  modal path reads it (the renderer gets the payload over luna).

### 1.6 What will actually kill the modal on the rooted TV (ranked)

1. Blackhole the remaining NSU hosts in early-boot `/etc/hosts` (same mechanism already used):
   `nsu.lge.com`, `snu.lge.com`, `snu-dev.lge.com` (+ consider iptables DROP to
   `156.147.69.32` for the hardcoded-IP path). Check fails → no response → `NSU_CreateUpdateAlert`
   never fires; `.lastNSUUpdateFailLog` gets written instead (harmless). [INF; highest
   confidence, reversible, keeps Settings > Software Update page functional for manual checks]
2. Turn off the boot check the intended way: `luna://com.webos.settingsservice/setSystemSettings`
   `{"category":"support","automaticUpdate":"off"}` — this is the official toggle; the daemon
   honors it for auto checks. [INF from key presence; verify on live box with one boot]
3. Kill the daemon spawn entirely: mask the ping unit (already done) AND remove the D-Bus
   activation by overriding `usr/share/dbus-1/services/com.webos.service.update.service` (bind-
   mount an empty `.service` over it at boot) — then tvpowerd/eplmanager getStatus calls fail
   harmlessly (returnValue:false) and the daemon never runs. Side effect: manual "check for
   update" and USB-update flows break. [INF]
4. Neutering `/usr/sbin/update` (chmod 000 or stub) also works but is cruder than 3 and identical
   in blast radius.
NOT sufficient (already proven live): hotelMode.swUpdateEnable edit, db8 cleanup, cmn_data
cleanup. NOT needed: WAM localStorage touch.

## 2. Boot topology and remaining disableable work

### 2.1 How boot is structured [OBS]

- PID 1 = systemd (`sbin/init -> ../lib/systemd/systemd`). LG's bootd (`usr/sbin/bootd`,
  "simplified upstart-like component") emits phase events and reads `etc/palm/bootd.json`
  (also overridable at `/var/luna/preferences/bootd.json`).
- Boot phase targets: `webos-cbd.target` (cold boot daemons) → `webos-mbd.target` (minimal boot
  done) → `webos-bd.target` → `webos-rbd.target` (rest boot done), all in `lib/systemd/system/`
  with `.wants/` lists. `sbin/initctl` is an LG shim: `initctl start X` → `systemctl start X`.
- The many `etc/init/*.conf` upstart-style jobs are vestigial on this image for service startup
  (systemd owns targets); `etc/init/update.conf` (`start on minimal-boot-done`, exec
  `/usr/sbin/update`) is the one that still matters — delete/blank it too when neutering the
  update daemon. [INF activation path, OBS files]

### 2.2 Snapshot boot and the double home launch [OBS]

- `etc/systemd/system/snapshot-boot-components.service` (kernel cmdline `snapshot`) starts
  ls-hubd/dbus/configd/surface-manager/sam/memchute, then:
  - `applicationManager/launch {"id":"com.webos.app.inputcommon","params":{"snapshot":true}}`
  - `applicationManager/launch {"id":"com.webos.app.home","params":{"snapshot":true},"preload":"full"}`
- `lib/systemd/system/scripts/com.webos.app.fullhome.sh` (unit `com.webos.app.fullhome.service`
  in `webos-cbd.target.wants`) then:
  1. reads `settingsservice general.defaultApps` → home
  2. `closeByAppId {"id":"com.webos.app.home","forceMode":true}`
  3. `launch {"id":"com.webos.app.fullhome","params":{"snapshot":true},"preload":"full"}`
- So every snapshot boot restores **com.webos.app.home** from CRIU only to kill it and restore
  fullhome. [LIVE] matches the observed "double home launch".
- `usr/bin/webos-preload-manager` (`preload-manager.service`, webos-bd.target.wants) then waits
  `startAfter=2`, CPU<40% (`etc/palm/webos-preload-manager-conf.json`), and preloads
  `com.webos.app.home` + `com.webos.app.fullhome` AGAIN ("kill preloading app" logic) — a third
  churn of the same binaries in the post-boot window. [OBS config + strings]

**Fix options (rank)**: remove the `com.webos.app.home` launch from
snapshot-boot-components.service (keep inputcommon), and/or mask `preload-manager.service`.
Expected: one fewer CRIU restore + kill cycle per snapshot boot (~0.5–2 s CPU, memory churn)
[INF estimate]. Risk: medium — home may exist to pre-warm Qt/WebEngine resources for fullhome's
first draw; A/B a cold and a snapshot boot before committing.

### 2.3 CRIU checkpoint copying [OBS]

`criu_copy_img.service` (webos-bd.target.wants, oneshot `lib/systemd/system/scripts/criu_copy_img.sh`):
- copies every app checkpoint in `/tmp/checkpoint` → `/mnt/lg/cmn_data/checkpoint` (eMMC),
  `ionice -c 3` (idle), verifies `MD5SUM`s, symlinks `pages-*.img`, touches
  `/tmp/finish_criu_boottime_copy`.
- I/O is proportional to snapshot image size; big webapp snapshots make this a real boot-window
  copy job. If skipped: after a power-cut cold boot the snapshots can't be resumed → one cold
  boot, then the system re-checkpoints (self-healing).
The CRIU daemon itself (`etc/init/criu.conf`) only enables with `criu_enabled` cmdline + non-cold
power mode. `memchute`/`memchute-ready` set vm tunables (swappiness 100, min_free 8M, workingset
80M) and start the low-mem notifier — one-shot, cheap; **keep** (part of the suspend/snapshot
memory machinery; disabling risks OOM on the 2 GB box). [OBS scripts]

## 3. Modal follow-up: alert creation on a failing check + surgical disable

Live falsification absorbed: all three NSU endpoints cut before the check window, modal still
shows → §1.4's "fresh successful check" is refuted as the operative gate. Revised below.

### 3.1 Does the FAIL/TIMEOUT path itself create NSUUpdateAlert? — NO [OBS]

- The only production creation site is `fcn.0002431c` ("version found" decision): strings
  `"NSU Update Version is found(AutomaticUpdate:false) - create Update popup"` /
  `"NSU Auto Update Version is found(AutomaticUpdate:true) - start update right now"`; it arms
  the `NSUUpdateAlert` timer (`update_createTimerSetDataAndSetStatus` + `"nsuVersionCheckTimer"`)
  with a 3 s delay when not manual (`"%s - bModeManual is false. There is 3 sec delay."`).
- Its caller is the NSU response processor in `fcn.00028a54` (parses `bModeManual`, `epkVersion`,
  `imageSize`, `deltaImageSize`, `RemainDownloadTime`, `RANGE_SIZE`) — i.e. a parsed server
  response is required.
- The failure path is separate: `"ERROR: Network is disconnected during version check"`,
  `"bStart is false => move to MSG_NSU_AUTOVERSIONCHECK_FAILURE"`, retry counter `_gNSURetryCount`
  — no alert creation on that branch. `NSU_CreateFailToastPopup` texts are download/install
  failures, not "update available".

### 3.2 So what re-raises the modal with the network dead? — LOCAL update state [OBS paths / INF gate]

them at boot:

| `/mnt/lg/cmn_data/swupdate/deltaImageUpdateInfo.json` (+`.backup`) | `NSU_SaveDeltaImageUpdateInfo` | `NSU_LoadDeltaImageUpdateInfo` ← `_NSU_CheckResumeCase` |

The 10:50 signature now decodes cleanly: check succeeded (pre-blackhole) → header download
STARTED (`HeaderReceivedCallback`) → download failed → `.lastNSUUpdateFailLog` + `.UpdateIsInprogress`
+ AppStore content persisted. At every later boot the daemon re-reads that state:
`_NSU_CheckResumeCase` → `"## Resumed Case - jump to download Package."`, and `NSU_TimerCreateAlert`
prints **`"NSU Update file detected."`** before posting `NSUCreateUpdateAlert` with
`alertInfo->bResume : %d`. No network needed to re-show the modal. [INF exact branch, OBS all
strings/paths]

**On-box confirmation list (one `ls` each, the smoking gun is the first):**

- `ls -la /mnt/lg/cmn_data/` WITH dotfiles — expect `.UpdateIsInprogress`
- `ls -la /mnt/lg/cmn_data/swupdate/` with dotfiles (`Image_Update_Info.xml*`, `deltaImageUpdateInfo.json*`)

### 3.3 Minimal surgical disable (ranked)

(a) **Blanking the D-Bus activation files** — `usr/share/dbus-1/services/com.webos.service.update.service`
and `usr/share/dbus-1/system-services/…` (both `Type=dynamic`, `Exec=/usr/sbin/update`) [OBS].
`Type=dynamic` means ls-hubd spawns the binary only when a caller arrives; no file → `getStatus`
callers get `returnValue:false` (async `onFailure` — no caller blocks: tvpowerd/eplmanager/
contentminer/legacy-broadcast all fire-and-callback [OBS luna patterns]). Files are on the RO
squashfs → one bind-mount each in the existing early hook (same hook that already edits
/etc/hosts; single-file mounts are not startup.sh script surgery). After this, NOTHING spawns
the daemon: bootd never runs it because — see (b).

(b) **bootd/`etc/init/update.conf` respawn behavior** — the conf has NO `respawn` directive
([OBS] conf text: `description`/`start on minimal-boot-done`/`script` only), so even if bootd
still processed it, an instant exit does NOT loop (bootd = "simplified upstart"; respawn only
with the directive, cf. bootd.conf's own `respawn`). Note also: bootd's binary contains NO
`/etc/init` or `update` references at all ([OBS] strings), and `sbin/initctl` is an LG shim
mapping to `systemctl` — the live daemon is most plausibly spawned exclusively via D-Bus
activation; `/tmp/update-first`/`update-respawned` are the daemon's OWN restart markers, not
bootd state. [INF] Do NOT make the binary exit non-zero instantly (crashd noise, unknown bootd
task semantics); prefer removal of the spawn path.

(c) **Config/settings that disable check or alert** — exhaustively, from the binary:
- `hotelMode.swUpdateNotice:"off"` suppresses ONLY when `hotelMode.enableHotelMode:"on"`
  (`"ERROR : Do not create NSU Alert when hotel mode is enable if notice is disable."`).
  Enabling hotel mode to reach that gate is disproportionate. [OBS]
- `support.automaticUpdate:"off"` does NOT stop the popup — the found-update branch is
  `"AutomaticUpdate:false - create Update popup"`; automaticUpdate only selects
  auto-install-now vs popup. [OBS] (Corrects §1.6 option 2: demote it.)
- `update/setNSUMode` is `user`|`engineering` (factory image mode), not an on/off switch. [OBS]
- No configd key read by the daemon (`tv.model.*`, `tv.hw.*`, `tv.config.*`, …) disables the
  check. [OBS `adapter_update_getConfig` key list]
- EULA gate (`generalTermsAllowed` / `NSU_SubscribeEULAStatus`) can stop the auto check but is a
  global personalization lever — not surgical. [OBS strings]
→ **No clean data-side kill exists.** The lifecycle kill (a) is the surgical one. Optional
refinement keeping the daemon alive: an ls2 role override denying
`com.webos.service.update` → `com.webos.notification` (roles live under `/usr/palm/roles`,
overridable per snapshot-boot-resume.sh via `/var/palm/ls2/roles/{prv,pub}`) — plausible but
merge semantics UNVERIFIED on-box; try only if (a) is unacceptable.

(d) **Exact alert payload + renderer-side drop** — payload built in `NSU_CreateUpdateAlert`:
```json
{ "alertId": "NSUUpdateAlert", "type": "modal",
  "message": "The latest version of the software is available for your TV.
              Do you want to update now?<br>(Software Update: 04.xx.xx)<br>
              * Please use LG TV Remote Control.",
  "buttons": [ { "label": …, "onclick": "luna://com.webos.service.update/startUpdate",
                 "params": { "confirm": … }, "focus": … } ] }
```
[OBS rodata 0x68010–0x6808c, 0x62c68, 0x682e8]. `com.webos.app.notificationcenter` renders all
`com.webos.notification` alerts generically and has **no alertId filter** [OBS main.js];
`notificationmgr` has no per-app/per-alertId block list either — its `NOTIFY_ENABLE/DISABLE`
strings belong to the hospitality signage schedule (`com.webos.app.commercial.alert`, XML
schedule parser), not a consumer block mechanism [OBS rodata 0x4d2c0–0x4d618]. So there is no
supported "drop NSUUpdateAlert" switch; renderer-side blocking would mean patching
notificationcenter's bundle (heavier than (a)).

**Bottom line:** (a) + clearing §3.2 state = complete, boot-safe kill. The late (+105 s) hook
cannot do (a); it CAN do the state-clearing deletions and a `luna-send closeAlert`-style cleanup,
but boot-time modal suppression requires the early-hook bind-mounts (2 files) or whatever
persistent-mask mechanism already disables the other units.

## 4. Boot critical path — per-item implementation notes

Constraint honored: no early startup.sh surgery; only persistent unit masks/drop-ins (the
mechanism that already disables the existing list) or data/settings changes.

### 4.1 Snapshot double home launch

Decision input [OBS `lib/systemd/system/scripts/com.webos.app.fullhome.sh`]:
```
defaultApp=`luna-send … getSystemSettings '{"category":"general","key":"defaultApps"}' | grep home | …`
if [ $defaultApp == "com.webos.app.fullhome" ]; then
    closeByAppId {"id":"com.webos.app.home","forceMode":true}
    launch {"id": "com.webos.app.fullhome", "params": { "snapshot": true }, "preload":"full"}
fi
```
It reads the **settingsservice `general.defaultApps` (`.home` field)** — not a configd key.
Since the box's defaultApps.home IS fullhome, the script always closes home + launches fullhome.

Minimal one-change edit: a persistent drop-in
`/etc/systemd/system/snapshot-boot-components.service.d/nohome.conf` that resets the ExecStart
list (`ExecStart=` empty line) and re-declares all lines EXCEPT the `com.webos.app.home` launch —
i.e. keep ls-hubd/dbus/configd/surface-manager/sam/memchute starts and the inputcommon launch.
The script-side `closeByAppId` then fails harmlessly (luna-send error, no `set -e`, no `&&`
chaining [OBS]) and fullhome still launches + CRIU-restores. [OBS]
- Do NOT flip `defaultApps.home` away from fullhome: the script would then skip the launch and
  boot would strand on home (or nothing). [INF from script]
- Dependencies on home-first: none found. CRIU image selection is per-app (checkpoint dirs are
  per-app; `criu_copy_img.sh` iterates `/tmp/checkpoint/$dirs` independently). inputcommon is
  launched BEFORE home in the same unit and is untouched. eim/foreground tracking sees fullhome
  arrive moments later. Residual unknown: whether `com.webos.app.home` pre-warms shared
  Qt/WebEngine resources for fullhome's first draw [INF] — A/B one cold + one snapshot boot.
- Only affects snapshot boots: the unit has `ConditionKernelCommandLine=snapshot`; cold boots
  don't run it. [OBS]

### 4.2 configurator-activity.service (blame 7.0 s)

[OBS unit] oneshot, `Requires=ls-hubd configurator-db8, After=… activitymanager, BindsTo=activitymanager`:
`ExecStart=luna-send -n 1 -f palm://com.palm.configurator/run '{"types":["activities"]}'`.
It feeds every `etc/palm/activities/*.json` (incl. the already-disabled `com.webos.appUpdateService`
and mostly-bloat entries: acr, admanager, adoverlay, membership, magicnum, livepick, dial, nlp…)
into activitymanager's db8. Consumers: activitymanager triggers only.
- The 7 s is the synchronous registration round-trip while activitymanager comes up — it is
  serialization, not CPU.
- Skip = mask the unit: boot activities don't register that boot. Everything already disabled is
  unaffected; risk is losing any *useful* activity (e.g. db8 housekeeping ones). Verdict:
  **safe to mask; one-change-at-a-time; verify no db8-compaction activities are wanted**
  (`ls /etc/palm/activities` on-box). `configurator-db8.service` (dbkinds/filecache/
  dbpermissions) must STAY — db8 consumers depend on kinds. [OBS script]

### 4.3 settings-service-recovery.service (blame 6.3 s)

[OBS unit] oneshot, `Requires/After=settings-service.service`, `RemainAfterExit=no`;
[OBS script] does exactly three things:
1. `luna://com.webos.surfacemanager/showSpinner {"show":false,"owner":"com.webos.settingsservice"}`
   (unless factory cmdline) — hides the settings spinner,
2. `echo settingsservice_ready > /tmp/settingsservice_ready` — **milestone file** consumed by
   `legacy-broadcast`, `videooutputd`, `pqcontroller`, `tv-reservation-agent` [OBS grep],
3. `/usr/bin/recover_hdr_psm.sh || true` — picture-mode (PSM) recovery for HDR/Dolby-Amazon
   special modes: two getSystemSettings reads + at most one write. [OBS script]
Not a timeout — the 6.3 s is `After=settings-service.service` wait + the luna round-trips.
**Do not mask**: `/tmp/settingsservice_ready` gates four daemons. Optional trim later: the
recover_hdr_psm step (drop-in replacing ExecStart with just the echo + spinner hide) — low
value, skip for now.

### 4.4 com.webos.app.multiview.service (blame 5.2 s)

[OBS script `lib/systemd/system/scripts/com.webos.app.multiview.sh`] — it does NOT launch any
app. It is a settings-RECOVERY oneshot: reads `option.multiViewStatus`; if "on", sets it "off"
and re-enables caption/sound UI descriptors (`captionEnable`, `avSync`, `visualImpaired`, …).
If not "on": `echo No need to recover multi view settings`. Confirmed two-input-multiview
plumbing only; nobody queries it (it only WRITES settings). [OBS grep: referenced only from its
unit + script]. The 5.2 s blame = `Requires/After=settings-service.service` wait for a no-op
check. **Safe to mask**, zero fallout. One change: `systemctl mask com.webos.app.multiview.service`.

### 4.5 lsm-ready (blame 9.1 s)

lsm = the ls2/WebView stack readiness milestone, not a worker:
- `etc/init/lsm-ready.conf`: on the `lsm-ready` event, first emission writes
  `/tmp/lsm-ready` (`echo date > /tmp/$UPSTART_JOB`), later emissions restart WebAppMgr.
- `lib/systemd/system/lsm-ready.path`: `PathExists=/tmp/lsm-ready` → `lsm-ready.target` →
  `lsm-ready.service` = stop+start of `webapp-mgr`, `booster`, `maliit-server`. [OBS]
- `webapp-mgr.service` itself has `ConditionPathExists=/tmp/lsm-ready` — WAM does not start
  until the file exists. [OBS]
- Producer: `usr/bin/initctl` ("STATUS=initctl notifies ready event", knows `lsm-ready`); bootd
  does NOT emit it ([OBS] no string in bootd). Some ls2-stack service notifies ready via initctl.
Verdict: **mostly parallel slack + one deliberate WAM bounce**. The 9.1 s is time-to-milestone
(waiting on ls-hubd/surface-manager), not consumed CPU. Do not mask the path/target (breaks the
WAM start gate); optionally mask ONLY `lsm-ready.service` to skip the stop/start bounce of
webapp-mgr/booster/maliit — that bounce is real boot work, but LG added it deliberately
("Restart WAM/MaliitServer when lsm-ready is emitted more than once"), so treat as Tier C:
test UI stability before keeping. [INF]
